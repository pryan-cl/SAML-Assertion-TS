Failure modes, ranked by how often they turn out to be the answer

SAML

  • Audience mismatch. The <Audience> must match the SP's entity ID character for character. Trailing slashes and http vs https are the usual culprits.
  • Signing certificate rolled. The SP is usually pinned to a thumbprint. Compare it against the tenant's active signing key. Entra's expiry notice goes to the app's notification address, which is often a person who has left. See managing signing certificates.
  • Response not signed. Entra signs the assertion only by default. SPs requiring a signed response need Signing Option → Sign SAML response and assertion.
  • NameID is the wrong thing. Default source is user.userprincipalname. SPs keying on email need format emailAddress and usually source user.mail. UPN and mail differ more often than people expect in practice. See customising claims.
  • Claim names don't match. Entra emits schema URIs; many SPs want short names. Clear the namespace field to get a bare name. See customising claims.
  • User not assigned. Assignment required plus a user outside the assigned groups is AADSTS50105, before any assertion exists. Do not trust a per-user view to tell you: someone assigned through a group, especially a nested one, can look unassigned there. Read the app's Users and groups list rather than the user's. See assigning users and groups.
  • Clock skew. A drifted SP server rejects a good assertion as expired.
  • Reply URL mismatch. AADSTS50011. The assertion's Destination has to be one of the app's registered reply URLs, character for character. See redirect URI restrictions.

OIDC / OAuth

  • v1 versus v2 endpoint. The issuer differs and so do the claims. An SP validating a v1 issuer against a v2 token fails on iss.
  • Wrong token handed over. A Graph access token is not an id_token for the SP. Check aud.
  • sub is per-application. Use oid for anything that has to correlate across systems. See the id_token claims reference.
  • email claim missing. Not emitted unless the user object has a mail value and the claim is configured.
  • Group overage. Past the token size limit Entra sends hasgroups instead of the list, and SPs reading only groups see the user in none. See configuring group claims.
  • Expired secret. Looks like a total outage with no user-side symptom. AADSTS7000215 / 7000222.
  • Conditional Access. AADSTS53003 means policy blocked it, not that the integration broke.
  • Conditional Access in report-only mode. The only failure here you can see coming. The sign-in succeeds today and stops working the day the policy is enforced, with nothing visible changing in between. The sign-in log names the policy under its report-only result, so raise it before the rollout rather than after. See report-only mode.

Getting the raw material

  • Browser. DevTools → Network, preserve log, reproduce the sign-in, find the POST to the ACS URL, copy SAMLResponse from the form data.
  • Token encryption defeats that capture. If the app has token encryption enabled the POST carries an EncryptedAssertion, and no amount of decoding reads it without the SP's private key. Nothing is wrong with your capture. Turn encryption off for the duration of a test, or work from the SP's own logs. See SAML token encryption.
  • Entra sign-in logs. Filter to the application, open the failed row, read the failure reason and correlation ID. Escalate with the correlation ID and UTC timestamp, not a screenshot. See sign-in logs.
  • Test in isolation. The enterprise app's Single sign-on blade has a Test button that reports the AADSTS code without involving the SP at all.
Read this before pointing anyone at the Live tenant tab. Asking a tenant administrator to consent an application into their directory is a governance decision, not a support step. It needs an app registration owned by your organisation, publisher verification so the consent screen names your company, a published privacy statement, and whatever security review your side requires. A page on a personal github.io subdomain asking an organisation for directory read access is shaped exactly like a phishing attempt, and a competent tenant administrator should refuse it. Host it on a company-controlled domain, or use pasted output instead.

Option A — pasted output, nothing to approve

The tenant administrator runs a read-only query in a tool Microsoft already owns, then pastes the result here. No app registration, no consent, no tokens in this page. This is the version to reach for on a support call today.

Send them to Graph Explorer, have them sign in, consent to the individual permission it prompts for, run the query, and copy the response. Or in PowerShell:

Connect-MgGraph -Scopes "Application.Read.All","User.Read.All","Directory.Read.All","AuditLog.Read.All"

# App configuration, signing certs, entity IDs, reply URLs
Get-MgServicePrincipal -Filter "displayName eq 'APP-NAME'" |
  Select-Object  |
  ConvertTo-Json -Depth 5

# The affected user, to compare UPN against mail
Get-MgUser -UserId "jdoe@contoso.com" -Property  |
  ConvertTo-Json

# Is the user actually assigned to the app
Get-MgUserAppRoleAssignment -UserId "jdoe@contoso.com" -ConsistencyLevel eventual -CountVariable c |
  ConvertTo-Json -Depth 3

# Recent sign-ins for the app (needs Entra ID P1 or P2)
Get-MgAuditLogSignIn -Filter "appId eq 'APP-GUID'" -Top 15 | ConvertTo-Json -Depth 5

Directory.Read.All is in that list for the assignment query alone. Microsoft does not accept User.Read.All for appRoleAssignments, and the only lower-privileged alternative it does accept is AppRoleAssignment.ReadWrite.All, a write scope this page will not ask anyone to consent. Drop the assignment query and the first two scopes are enough.

Graph Explorer equivalents, if they prefer clicking:

GET /v1.0/servicePrincipals?$filter=startswith(displayName,'APP-NAME')&$select=
GET /v1.0/users/USER?$select=
GET /v1.0/users/USER/appRoleAssignments?$count=true     (with header ConsistencyLevel: eventual)
GET /v1.0/auditLogs/signIns?$filter=appId eq 'APP-GUID'&$top=15

Why this page cannot borrow a Graph Explorer session

A reasonable thought, since Graph Explorer needs no app registration of your own. It cannot work, for three separate reasons:

  • Same-origin policy. Graph Explorer's token sits in browser storage under developer.microsoft.com. This page is a different origin and cannot read it. That boundary is the thing keeping every other site out of your session too.
  • The token belongs to a different app. It was issued to Graph Explorer's own first-party client ID, and the consent the user granted was granted to that app. Using it from here would be spending someone else's consent.
  • There is no broker API. Graph Explorer is a client of Graph, not an identity provider, so there is nothing to delegate through.

Setting the client ID field to Graph Explorer's application ID does not work either. Its registration does not list this page as a redirect URI, so you get AADSTS50011 straight away, and impersonating a Microsoft first-party registration is not a road worth starting down.

What the page does instead is build the query, copy it, and open Graph Explorer so they can run it in one paste. The Share link format Graph Explorer produces is not a documented API, so the deep link is best effort; the clipboard copy is the part that reliably works. Test it once and if the prefill stops working, the query is still on the clipboard.

Permissions the live checks need

The same set applies to Option B and Option C below, so it is listed once here rather than inside either of them. Option A needs none of it: the tenant administrator runs the queries themselves in a tool Microsoft already owns, and consents only to what that tool asks for.

Delegated scopeStatusUnlocksNotes
Application.Read.AllrequiredSSO mode, entity IDs, reply URLs, signing certificates and expiry, assignment requirementAdmin consent. The workhorse.
User.Read.AllrequiredUPN versus mail, account enabled, guest status, on-prem sync stateAdmin consent.
Directory.Read.AllrequiredApp role assignments, plus the group memberships behind themAdmin consent. Broadest of the set. Dropping it disables group-inheritance resolution, so the assignment check falls back to reporting that it cannot tell for any user assigned through a group, which is the normal case.

The four marked required are exactly what the page asks for. Adding a scope widens what a tenant administrator has to approve, so treat any addition as a real cost rather than a convenience.

Option B — the tenant registers their own app

This is usually the easiest yes. The tenant creates a single-page app registration in their own tenant, pastes the client ID and their tenant ID into the fields on the Live tenant tab, and gets the full live checks without extending any trust to a vendor. Their app, their tenant, their consent, their revoke button. Nothing to security review on your side because you are not asking for anything.

  1. Entra admin center → App registrations → New registration. Any name. Accounts in this organizational directory only.
  2. Redirect URI: platform Single-page application, value is the exact URL of this page. See redirect URI restrictions and registering an application.
  3. API permissions → Microsoft Graph → Delegated: the scopes marked required under Permissions the live checks need above. Then Grant admin consent.
  4. Copy the Application (client) ID and the Directory (tenant) ID from the Overview blade into the fields above.
  5. No client secret. This is a public client and does not need one.

Client ID and tenant ID are public identifiers, not credentials, so this page keeps them in localStorage to save retyping. Tokens are held in sessionStorage and never persist past the tab. Forget these IDs clears the stored config.

Option C — a multi-tenant app you own, if it gets approved

Same mechanics as Option B, except the registration lives in your tenant and every tenant has to consent it. That buys you a one-time setup instead of per-tenant setup, and costs you a security review, publisher verification, and a harder conversation. Set DEFAULT_CLIENT_ID in the script block to prefill it.

App registration

  1. Register the app in your own tenant. Supported account types: Accounts in any organizational directory.
  2. Add a Single-page application redirect URI with this page's exact URL. Registering it as Web instead is the single most common mistake and produces AADSTS9002326 about cross-origin token redemption.
  3. Complete publisher verification so the consent screen shows your company as verified, and set the privacy statement and terms URLs. See publisher verification.
  4. Add the delegated permissions marked required above. Do not request offline_access. Without it there is no refresh token, so the session dies with the tab.

Admin consent

Every required scope needs an administrator. Either the tenant administrator ticks Consent on behalf of your organization at first sign-in, or you send a consent link ahead of the call. See granting tenant-wide admin consent.

https://login.microsoftonline.com/{their-tenant-id}/adminconsent?client_id={your-client-id}&redirect_uri={this-page-url}

Either way, tell them plainly that consent is tenant-wide and persists until revoked, and show them where to revoke it: Entra admin center → Enterprise applications → your app → Permissions, or delete the service principal outright. Offering the revocation path unprompted is what makes the ask credible.

What this page does with the token

  • MSAL cache is sessionStorage, so closing the tab discards it. No tokens in localStorage, which holds only the client and tenant IDs described above.
  • No refresh token is requested or stored, so nothing here can resume a session later. Inside an open tab MSAL would otherwise renew silently against your existing Microsoft sign-in for as long as the tab stayed open.
  • A signed-in session is capped at two hours, applied whether the token still works or not. At the cap the session ends, anything read is cleared from the page, and signing in again asks for credentials rather than passing you straight through. A tab left open cannot hold a live read on the tenant's directory indefinitely.
  • Every call is a GET. There is no write path anywhere in this file.
  • End session clears the cache and signs out.

Static page, no backend, no analytics, no storage. Outbound requests happen only when you sign in to a tenant or run the optional token signature check, and go to Microsoft endpoints.
